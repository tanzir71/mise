# Public order admission — M33 in progress

The backend can admit a customer request as one real order and issue its original tracking capability atomically. This is an implementation increment; public ordering has no connected customer interface yet, and M33 remains open. The new `public` Edge Function is disabled unless the installer explicitly sets `MISE_PUBLIC_ORDERS_ENABLED=true`. Existing customer-link previews remain off by default. GitHub workflows and Pages publication stay held.

The owner or an assigned manager first approves a publication of the actual M20 shop snapshot. The authenticated publication RPC derives its business and outlet from current authorization, checks the current catalogue and records an audit. Optional table scope is approved here, never supplied by a customer. Publication secrets are chosen by the future owner client and only their hashes are stored. An original retry cannot change a publication or reactivate a revoked one. Closing an unpublished attempt fences delayed creation.

`POST /functions/v1/public/orders` accepts a closed request shape, a captcha-free honeypot, the shop capability and the customer's original tracking secret. No customer account, API key or owner session is required. Customer input cannot choose a business, outlet, actor, record total, discount, payment confirmation or financial table. The request reference derives from the tracking-secret hash, so a reference alone cannot plant an earlier closure. Canonical source, original identities and secret hash bind every retry. Inspecting or closing uses that same complete original request; it never manufactures a replacement.

The service prepares current scoped records, a server clock and an expiring completion ticket. The existing Core order command produces the order and creation audit. SQL rechecks current authority, publication, catalogue context, sequence, source, lines, integer totals and the complete audit before committing the order, system audit, purpose-bound tracker and receipt together. Context conflicts retry the original request with a fresh preparation. A lost completion response can be inspected without creating a duplicate. Closing an unfinished attempt blocks its delayed finalizer; closing a completed attempt returns its real receipt rather than claiming that the order was cancelled. Tracker revocation is reflected on replay and never creates a replacement link.

The actual audit actor is `system/public-order`. The publishing member is retained only as the responsible member in the existing `createdBy` and `handledBy` fields. Customer contact is literal request data, not proof of phone ownership and not an automatic match to a khata account. New orders record cash pending, with no sale, balance entry, wallet confirmation or credit charge. The requested payment preference stays in the original source for the shop to review.

Published catalogue selections keep their approved integer prices; a changed live price needs review. Free text is retained completely as inert source and unpriced request lines, including long Unicode lists. Published M20 delivery notes contain no numeric delivery fee, so delivery adds an unpriced “Delivery fee to confirm” line. A shop must explicitly price it, including genuinely free delivery, before the total becomes known. Table orders use only the publication's approved table. No arrival estimate, delay, substitution approval or payment is inferred.

Private forced-RLS tables hold publications, secret-bound attempts and one fixed installation budget. Raw API roles have no table access. Owner publication/revocation RPCs require the live verified phone account; only the server role can call preparation/completion. Public wrappers use invoker security, and privileged functions live in the private schema with empty search paths. No provider, scheduled job, new credential or IP-indexed counter is introduced. The HTTP handler bounds bodies, response size and the complete backend-request lifetime, rejects redirects and returns only copied customer receipt fields.

Each installation owns its backend, exact allowed origins and existing server key. Empty optional limit settings use 300 HTTP admissions and 30 new attempts per shop per server minute; valid configured limits are integers from 1 to 60,000. Existing original retries can proceed at the shop limit, while the installation limit still applies. Unknown capabilities consume the fixed installation budget. Limits are installation policy, never customer input. Actual deployment identifiers and credentials stay outside tracked source and build output. See [installation configuration](configure-services.md).
