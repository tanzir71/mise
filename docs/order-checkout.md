# Customer prices, swaps and payment choices

The opt-in `publicOrders` preview lets a corner-shop customer review the shop's actual prices, accept or decline each proposed substitute and confirm the same order without an account. Cash is selected first. Wallets appear only after the installation's owner or assigned manager configures public receiving accounts. Khata appears only after a separate permission for this exact order and customer. The preview stays off by default.

Each installation supplies its own hosting, backend connection, phone sign-in, allowed origins and private service environment. Settings › Shop link › Payments starts with empty receiving accounts. Enter the shop's public receiving phone and payment link; no maintainer account, personal number, provider credential or verification code is required. Cash and the existing message/copy path remain usable without a wallet provider. Privileged provider credentials stay in the installation's backend. See [service configuration](configure-services.md).

An owner or assigned manager can allow khata from the order detail after synchronizing that exact customer, order revision and currency. The screen shows the current balance, account limit and order maximum, and requires an explicit choice to reveal those terms on this order link. The backend checks the actual linked customer and current-currency account. A matching phone or name cannot grant access. A later order change invalidates the old permission for new confirmation; the original permission and its receipt remain historical.

The customer must choose Yes or No for every pending swap. No leaves the proposed item out and updates the total. It does not claim that the original item is available or mark inventory unavailable. The full original quote and explicit decision remain in the saved action and audit. Missing answers cannot be submitted as No. The shop may have entered prices while the order is still Requested; the tracker keeps that real status until the accepted choices advance it.

Confirmation uses the existing Core order, status and settlement commands. Cash and wallet choices leave payment pending and create no sale or ledger entry. Permitted khata rechecks the exact order, actual ledger balance, limit and allowance, then atomically creates one real credit sale and charge. Customers cannot override a limit. The system confirmation is identified in the audit; the publishing member remains the legacy responsibility reference.

After a wallet confirmation, the customer checks the current receiving account before opening it. A removed account, revoked link, recorded payment or finished/cancelled order cannot offer an old target. The receiving number and link have Copy actions, and Mark done records only the step on that page. It does not claim that the shop received money. The immutable confirmation receipt describes payment at confirmation; current payment facts come from the fresh tracker.

Only the original tracker created by an approved public-order admission can confirm that order. A manually issued read-only tracker cannot acquire write permission by adding a flag. Public requests carry the original capability and choices, without owner Auth, an API key, an account selector or a customer-selected ledger. Fixed backend RPCs recheck the live link, issuer, assignment, expiry, original source and complete current context before any write. Restricted metadata tables force RLS and have no direct API grants.

The customer browser saves and reads back the full quote, hash, decisions, payment choice and allocated identities under a native lock before sending confirmation. Another tab cannot replace an unconfirmed original. A lost reply keeps that same action for inspection or retry; closure is saved before the network request, including while offline. Closing an already-applied action returns its real receipt and does not invent cancellation. Storage failure or unavailable locks leave the manual copy path available without sending a new action.

If a later tracker read fails or the link is revoked, its old prices, current status and receiving accounts are hidden. The same browser can still copy its own saved choices or retain closure for that original. Previously received data is not authority for a new confirmation or payment account. Owner settings use a separate journal bound to the original connection, signed-in account, native operator and outlet/order. Account changes and late replies cannot confirm another account's action. Cached contexts cannot authorize a new setting, and an older initial read cannot replace a newer observation.

Checkout has separate installation-wide and per-link request budgets. `MISE_PUBLIC_CONFIRMATIONS_PER_MINUTE` and `MISE_PUBLIC_LINK_CONFIRMATIONS_PER_MINUTE` default to 300 and 30 requests per server minute; valid values are 1–60,000. Quote, confirmation, inspection, closure and receiving-account requests each count. Invalid configuration keeps the public handler unavailable. The existing customer-reader and order-admission budgets retain their own state.

The English and Bangla interface follows the supplied C09, Storefront Payments and M14 references, using the original icon exports and shared tokens. Timing details keep their real data; no delivery estimate or medicine-equivalence claim is invented. The confirmation bar occupies the page footer, with 44 px controls and keyboard-accessible long original requests. Verification covers the five required widths. The existing order, sync and portable-backup formats and the 60,000/75,000-byte offline form limits remain unchanged.
