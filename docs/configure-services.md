# Configure services for your Mise installation

Your shop controls its hosting, backend and provider accounts. The Mise maintainer does not provide personal service accounts, API keys or verification numbers. Counter sales, orders, stock, khata and backups remain available locally while optional services are unconfigured.

The shop's installer configures the backend once. Owners and staff then use their own phone or enrolled screen; each staff member does not need a separate provider account.

Configure only the features available in your installed release. Backend configuration does not enable unfinished features or establish successful SMS or notification delivery by itself.

## Cloud connection

Use a Supabase project controlled by your installation. Deploy this repository's migrations and Edge Functions to that project, following the installed CLI's `--help` for its current commands. Configure the backend values listed in `supabase/functions/.env.example` in that project's secret manager. Set the exact origins for your deployed app. Generate fresh installation-specific signing keys and PIN peppers; never reuse the development installation's configuration.

In Mise's cloud setup, enter that project's HTTPS URL and publishable key on the device. These are connection settings, not an administrator credential. Never enter a secret/service key or provider password into the connection form. Keep actual connection values out of the repository and public build variables. Supabase distinguishes [publishable client keys from privileged server keys](https://supabase.com/docs/guides/getting-started/api-keys).

## Phone sign-in

The installer enables phone authentication and configures the shop's chosen SMS provider in its Supabase project. Provider credentials stay in the backend's protected settings. Enable phone verification; do not auto-confirm phone numbers. Keep email and anonymous sign-in disabled for this installation. Allow the intended owner/manager accounts to sign up or provision them according to the shop's access policy.

Follow [Supabase's phone-login setup](https://supabase.com/docs/guides/auth/phone-login) for the selected provider. The user enters their own phone number in Mise and explicitly requests a code. Mise checks whether phone sign-in is ready before requesting an SMS. If setup is incomplete, use the guide to finish it and continue local work in the meantime.

Provider billing and delivery settings belong to the installation's account. Test an actual code from the installation after configuring it; an automated local test does not establish real SMS delivery.

## Observed payments (opt-in preview)

The `ownerTasks` preview uses the installation's existing connection and confirmed owner/assigned-manager phone sign-in. Apply the repository's payment-source and receipt-picker migrations to that installation's backend. No additional provider, credential, receiving number or environment variable is required for manual observation review. **Add payment by hand** records literal source for a person; it does not verify a provider or record money. Select an actual eligible backend receipt and explicitly confirm its match. If no receipt exists, record the actual collection through the normal order, counter or khata flow first.

Saved payment requests keep their full source and original identity on this device. After a lost reply, check or close that original before replacing it. **Saved payment requests from any outlet** can reopen the original account after outlet access is removed, with a separate recovery connection/sign-in supplied by the installation. Offline private copies and verified completed archives contain originals and receipts, without Auth tokens or provider credentials. They are separate from the shop backup. See [native payment review](https://github.com/tanzir71/mise/blob/main/docs/payment-sources-native.md).

## Desk notifications and device setup

The installer configures the installation's own alarm signing key, VAPID keys and HTTPS contact page in its backend. Scheduler configuration and Vault references stay private. An owner chooses the outlet warning settings; each desk explicitly enables browser notifications. Staff screens are paired to that installation and signed in with a staff PIN.

Until notification setup is ready, the cached Inbox, visible warnings and manual controls remain the working path. Verify actual notification delivery on the intended device after opting in.

## Staff shift links (opt-in preview)

The `staffTeam` preview uses the installation’s existing phone sign-in for its owner or assigned manager. In Team, save a member with their own staff link enabled, reopen their editor and create a 30-day link. Contact numbers and staff links do not create phone sign-in accounts. Share the complete link privately with that member; it contains no administrator key or owner session. The member can use it in English or Bangla without signing in.

The installer deploys the repository’s staff migrations and `public` Edge Function to its own backend. Staff links have an independent `MISE_STAFF_LINKS_ENABLED=false` default; enable this only for the available preview in that installation. The handler reuses that installation’s private `MISE_SERVICE_API_KEY` and exact `MISE_ALLOWED_ORIGINS`. It does not require a new SMS account or a maintainer phone number. The service key stays server-side. Optional `MISE_PUBLIC_STAFF_REQUESTS_PER_MINUTE` and `MISE_PUBLIC_STAFF_LINK_REQUESTS_PER_MINUTE` accept integers from 1 to 60,000, defaulting to 600 total requests and 60 per staff link per server minute. Reads, taps, original checks and closures all count. Invalid configuration keeps the endpoint unavailable.

A staff link reveals only that member’s shift and recorded attendance at the selected outlet. A new tap keeps its complete original in that browser before it sends. After a connection failure, check that saved tap before retrying or closing it; a closure also stays saved while offline. If the link or browser storage cannot be used, copy the check-in message or tell the manager, who can log it by hand with their own name recorded. Revoking the link, removing the member or disabling their link method blocks fresh reads and taps. A genuine earlier receipt remains an acknowledgement of that exact original only.

The browser that creates a link retains its secret privately; the backend stores its hash. On another owner device, revoke the old link and create a replacement there. Never include staff links, provider credentials or connection values in repository files or public build variables. The paired-phone controls are described below. Task permission enforcement remains unfinished; this preview stays off by default.

## Shared-screen attendance backend (in development)

The repository includes a separate `staff-device` service, paired-phone roster and own-attendance controls behind `staffTeam`. Its installer-owned setting `MISE_STAFF_DEVICE_ENABLED` defaults to false. This increment does not deploy or enable that service. An installation that explicitly opts into the preview must apply the matching migrations, deploy its own device-access/device-pin/owner-pin and staff-device source, and configure its own private backend environment and exact allowed origins. Keep the server setting false until that installation is ready.

The preview reuses that installation's device pairing, owner-configured staff PINs and private service key. No additional provider account, maintainer credential or verification phone number is required. Optional `MISE_STAFF_DEVICE_REQUESTS_PER_MINUTE` accepts 1–60,000 requests per device/server minute and defaults to 600. The owner enables order-phone attendance in the member’s Team editor, then sets their PIN in Shared screens. An explicitly opted-in rider appears there even before a PIN has been set. Pairing QR codes forward the selected attendance/kitchen preview flags and public connection without including a PIN, device secret or staff session. Each person uses their own PIN; switching people signs out first. The attendance method grants only own attendance to riders or kitchen members on counters, with no cash or order access. Manual attendance remains available in Team. The [shared-phone notes](staff-device-screen.md) describe original-tap recovery and the remaining M34 work.

## Customer link reads

The installation's `public-read` function uses the existing backend server key and exact allowed origins. Optional private backend settings `MISE_PUBLIC_READS_PER_MINUTE` and `MISE_PUBLIC_LINK_READS_PER_MINUTE` control the installation-wide and per-link budgets. Empty values use 3,000 and 60 reads per server minute; valid configured values are integers from 1 to 60,000. Invalid values leave reads unavailable rather than silently weakening the limits. No additional provider account or secret is required. Deploy only the customer interfaces available in your release; configuring this endpoint does not enable unfinished tracking or khata pages.

The opt-in `customerLinks` preview adds controls to existing order and customer details. The record must already exist in the installation's backend, and the signed-in phone account must be its owner or assigned manager. Use Sync setup to configure that installation; no personal maintainer account is involved. The generated customer link includes the public API origin and a purpose-bound secret, with no API key or owner session. Treat the complete link as private to its customer. Copy it before leaving the page: its one-time secret is not saved locally. After reload or a lost reply, inspect and close the saved attempt before creating a replacement. Revoke unwanted links from the record's link list, including links issued on other devices.

Customer pages use only the shop contact explicitly published in the approved public shop link. Configure that number in the shop-link settings; the owner sign-in and customer's stored phone are never substituted for it. Public ordering and recorded shop estimates are separate opt-in previews. Swap consent, customer payment choices and customer task writes remain in development and are not enabled by this read preview.

## Public order submission

The `publicOrders` preview includes owner publication, customer submission, original-request recovery and automatic table tracking. Recorded arrival/ready ranges and server-observed delay notices are available in that preview; full M33 still needs shop price/swap acceptance and payment choices. Its separate `public` Edge Function stays disabled by default; do not enable it for general use merely because its migration is installed. When the complete flow is available, the installation deploys that function and explicitly sets `MISE_PUBLIC_ORDERS_ENABLED=true` in its own backend environment. It reuses `MISE_SERVICE_API_KEY` and `MISE_ALLOWED_ORIGINS`; no maintainer account or additional provider is required. Never put the server key in a customer link or browser configuration.

Optional backend settings `MISE_PUBLIC_ORDERS_PER_MINUTE` and `MISE_PUBLIC_SHOP_ORDERS_PER_MINUTE` default to 300 HTTP admissions and 30 new attempts per shop per server minute. Valid values are integers from 1 to 60,000; invalid configuration keeps ordering unavailable. Limits do not confirm payment, ownership of a customer's phone or successful provider delivery. The existing message path remains the manual fallback. See [the current ordering scope](https://github.com/tanzir71/mise/blob/main/docs/public-ordering-runtime.md).

Corner-shop checkout uses separate optional backend limits, `MISE_PUBLIC_CONFIRMATIONS_PER_MINUTE` and `MISE_PUBLIC_LINK_CONFIRMATIONS_PER_MINUTE`, defaulting to 300 checkout requests globally and 30 per order link per server minute. Each quote, original-action check, confirmation, closure and receiving-account check counts. Both values accept integers from 1 to 60,000. Invalid values keep the public handler unavailable. The installation owner enters their own public receiving phone numbers and payment links in Settings › Shop link › Payments; these start empty. Cash remains available without a provider account. Provider secrets belong only in that installation's private backend environment. Khata requires a separate owner/assigned-manager grant for the exact order, customer, currency and revision; a customer phone number does not grant access to a ledger.

In the opt-in preview, generate and sync the public shop snapshot, refresh access in Shop link settings and choose Publish ordering link. Table labels and link duration belong to the installation. Publishing confirms that snapshot and its capability; it does not configure the backend service. The original `/app/s/` WhatsApp page remains available, while the new `/app/o/` link includes the installation origin and public ordering capability in its fragment. The customer device saves its own original request before sending; after a lost reply, use Check original request or close the unfinished request before sending another. Disabling a shop link retains real existing orders and their individual trackers.

For a synced order, its owner or assigned manager can record a time range and an optional public note in the order detail. The first deadline remains visible after updates or withdrawal. Check or close an unconfirmed original before replacing it; reconnect with the original installation account after an offline reload. These controls use the same connection and phone sign-in, with no extra provider or credential. See [recorded estimates](https://github.com/tanzir71/mise/blob/main/docs/order-estimates.md).

## Customer khata (opt-in preview)

The installer applies the customer khata migration and deploys the repository's `public` function to the installation's own backend. `MISE_CUSTOMER_KHATA_ENABLED=false` keeps this endpoint off until that installation explicitly enables it. It reuses the private service key and exact allowed origins. Optional `MISE_PUBLIC_KHATA_REQUESTS_PER_MINUTE` and `MISE_PUBLIC_KHATA_LINK_REQUESTS_PER_MINUTE` accept integers from 1 to 60,000 and default to 3,000 installation-wide and 60 per link per server minute. Invalid configuration keeps it unavailable.

The `customerKhata` app preview requires `customerLinks`. An owner or assigned manager creates the customer's own khata link from the synced account. Links carry the installation's public origin and capability, with no owner session or administrator key. The owner supplies their public wallet receiving accounts in Settings › Shop link › Payments; these start empty. Customers see only current accounts in the ledger's currency. No SMS account, maintainer phone or provider secret is required. Opening a wallet does not record a payment; the shop records the actual collection. Asking for more time or questioning an entry creates an owner task, with no automatic balance or deadline change. See [the implementation and verification notes](https://github.com/tanzir71/mise/blob/main/docs/customer-khata.md).

## Other integrations

The default-off `ownerTasks` Inbox preview uses the same installation connection and verified phone account. Its migration adds task decisions, manual reply records, undo and original-request recovery; it does not connect a messaging or push provider. Installers can opt in with `?flags=ownerTasks` after configuring their own Sync setup. Saved originals can be reviewed and closed locally while offline; network requests still require fresh server authorization. Payment matching, personal recovery across unavailable outlets and general urgent notification choices remain in development. Keep privileged provider and VAPID values in the installation's private backend environment; existing kitchen notification subscriptions retain their current purpose. See [the task implementation scope](https://github.com/tanzir71/mise/blob/main/docs/owner-tasks.md).

The opt-in `liveStore` preview uses only the installation's existing Sync setup connection and verified phone sign-in. Apply both Live store migrations to that installation's backend. An owner can inspect every business they actually own; managers need a current assignment to the viewed outlet. No separate Live provider account, phone number, service secret or public function deployment is needed. The page checks recorded facts every five seconds while visible and offers Refresh now and Today on this device when the backend is unavailable. See [Live store](https://github.com/tanzir71/mise/blob/main/docs/live-store.md).

As capture, courier, payment and AI integrations are delivered, their account choices, connections, limits and tests belong in the installation's setup/settings or private backend environment. Keep privileged credentials on that backend. An unconfigured optional integration stays off and explains how to configure it; it does not silently use the maintainer's account.

Use an integration's connection test after supplying its settings. If an external service is unavailable, keep the original work and use the provided manual fallback. Share only redacted diagnostics, never credentials, when reporting a problem.
