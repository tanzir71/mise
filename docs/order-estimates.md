# Recorded shop estimates — M33 in progress

The default-off `publicOrders` preview lets the current owner or assigned manager record an arrival or ready-time range on an existing, synced order. The customer tracker reads that actual range and an optional note explicitly shown to the customer. Requested pickup times remain separate. The application does not infer traffic, distance, preparation duration, rider departure or a reason for a delay.

The shop chooses a range in minutes. The browser uses the last successful server observation and monotonic elapsed time to construct its absolute window; a wrong device wall clock cannot move that promise. The backend checks the current phone account, actual outlet assignment, order revision, estimate revision, bounds and unfinished status. An expired original can be inspected or closed, but cannot be newly published. A later range retains the first promised deadline. Withdrawal removes the active range while retaining that deadline and history. Undo restores the previous recorded range through a new, checked action; it never rewrites an earlier receipt.

An estimate has its own revision in restricted backend metadata. Price changes, preparation taps and ordinary status commands do not overwrite it or invalidate an acknowledgement. Estimate writes do not change orders, order revisions, events, preparation records, sales or credit entries. Immutable estimate actions retain their original account, complete source, prior estimate and receipt. Raw metadata tables have forced RLS with no client grants. The two authenticated RPCs recheck the verified phone owner/assigned manager; public links only reveal their own approved timing fields and public note.

Before HTTP, the owner browser saves and reads back the complete original action under a lock scoped to its account, connection, operator, outlet and order. A lost reply remains unconfirmed and blocks a replacement. Check or retry that exact original, or close it first. Closure is saved before any network check, including while offline; an actual backend closure fences a delayed original. Closing an already-applied change returns its real receipt and does not pretend to undo it. A deserialized cached context cannot authorize a new action. Locally saving an intent uses the still-current original SDK session and native operator; every HTTP effect and confirmed receipt retains full live phone-account verification. After a disconnected reload, reconnect with the original account to inspect the saved action. Copy estimate remains the manual message path.

The customer delay uses the backend observation timestamp and the earlier of the current range's end or the first promised deadline, with the wording “at the last check.” A range brought forward can become late before that first deadline. An offline page does not increment the delay from its own clock or claim a new live status. Updating or withdrawing the range does not erase the first deadline. Finished and cancelled orders show no active arrival estimate or late notice. English and Bangla use the installation's timezone and the bundled Bangla typeface. New metadata is optional, so old records and the existing forms remain readable.

Each installation supplies its own connection, phone sign-in and backend deployment through setup or its private environment. No new provider account, credential or maintainer number is needed. These connection-owned journals and private backend metadata are not added to the Phase 1 JSON backup. Keep the installation's own backend backup when moving that backend; local order backups and existing sync formats remain unchanged. No privileged value appears in a customer payload or repository template.

Focused checks use the actual phone Auth SDK, native storage, HTTP, Core-created orders and PostgreSQL roles. They cover lost completion, durable offline closure, an initial read held during recovery, an SDK/native operator change after SQL completion, exact undo, permission denials, wrong clocks, credential-free customer reads and completion. Historical delay scenes explicitly seed an earlier accepted promise, then update or withdraw it through the real owner controls. They do not claim that the backend accepts a newly backdated estimate. The 360–1440 px comparisons use the supplied M02/M03/M14 frames. The design's tinted delay surface is rendered as an accent word and line under the repository's status-colour rule.
