# M37 · Observed payment sources

This increment supplies Core contracts and guarded database operations for observed payments. It does not yet expose a native capture/matching form, client request journal or general notification subscription. `ownerTasks` remains off by default; M37 remains unchecked.

An observation preserves the complete source, reference, amount in integer minor units, currency, payment method, received time and actual recorder. Manual capture records its origin as `manual`; customer text cannot claim to be a verified provider notification. Bangla, NUL and unpaired UTF-16 code units survive encoded literal fields unchanged. Text is data, including any instructions it contains.

Capture creates one observed `payments` row and one urgent source task. It creates no sale, khata entry, order payment or provider confirmation. The task has no generic Allow, Fixed or Sent control: resolving a payment source requires its specific review operation.

Matching requires explicit confirmation of a current, actual recorded counter receipt, paid-order receipt or unreversed positive khata payment. Business, outlet, amount, currency, method and literal method name must agree. A sale belonging to an order must be selected through that actual paid order. Credit sales, closing adjustments, cancelled/returned orders and reversed payments cannot become eligible receipts. One actual financial record can match only one observed source. Reads and writes recheck the actual phone account's owner/assigned-manager rights rather than trusting role claims.

Matching resolves the source task and changes only association metadata. A later financial edit or reversal invalidates its recorded fingerprint and reopens urgent review. The immutable receipt from the original choice stays historical. Explicit dismissal requires a reason. Undo restores the previous association or review state; it never reverses or resurrects money. A voided receipt restored by metadata undo remains in review. Stale source/target fingerprints and delayed undo cannot overwrite a newer choice.

Every operation retains its exact original intent and immutable result under the original Auth account. Inspection and closure remain available to that account after outlet access is removed. Closing an unknown original prevents its delayed submission from creating a source. Exact retries do not add another source or audit event. Concurrent closures share a bounded daily account budget; new genuine observations and exact historical retries remain usable after that budget is reached. Business/outlet locking and the financial-record constraint protect competing matches. Different phone accounts can reuse a personal action ID without confusing the latest source revision or undo audit.

Each installation supplies its own connection, phone sign-in, provider accounts, credentials and numbers. This feature requires no maintainer account or provider credential. Privileged settings remain in the installation backend. The checked-in source contains no actual Supabase project or organization details. It introduces no provider request, scheduler or Edge-function deployment. General urgent push must later use explicit installation-owned choices; existing kitchen subscriptions retain their original purpose.

The migration was first generated with the pinned Supabase CLI and then aligned, without a body change, to the managed database's actual recorded version: `20261123220341_observed_payment_sources.sql`. All three new private tables deny direct access and force RLS. Only guarded read/action entry points are granted to authenticated accounts; anonymous and service-role callers cannot bypass them. Raw helpers remain private. The prior frozen owner-task migration is unchanged.
