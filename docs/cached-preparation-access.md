# M34 · Remembering withdrawn preparation access

A shared preparation screen now remembers an actual read denial across offline reloads. The ordinary Kitchen view hides its cached board and work controls until a newly authorized server read succeeds. **My saved taps** remains available for the current member's original history and explicit closure. No original ticket, action, receipt or financial fact is deleted or rewritten into new authority.

The installation owns its backend connection, device pairing and member PINs. This change needs no new environment value, provider, account, credential, phone number or maintainer-supplied verification. Existing previews remain off by default; workflows and publication remain held.

## Native denial and restoration

The negative status belongs to the exact device, business, outlet, member and PIN session. It uses a separate key in the existing native kitchen store, preserving the version-3 database and its historical board. An absent or cleared negative record never grants work by itself. Actual server authorization remains required on every request.

Read failures and live-stream authorization denials stop the current controller immediately. Their negative status is saved before the interface reports that the check is retained. The negative write is queued immediately and can finish after opening personal recovery or closing the view. Native source comparisons prevent an old member’s result from changing the next member’s status. If saving fails, the current view remains stopped and says that the browser could not retain the check; originals and manual recovery remain available. Expired or invalid PINs still require the member's own sign-in.

After the manager changes access, **Check now** or reconnect performs a real current read. Its verified response and native page commit can clear the negative status together. A serialized page, cached permission, local PIN claim, malformed response or failed network call cannot clear it. The response also carries the status revision observed before its request: a later denial in this controller or a sibling tab prevents an older authorized response from reviving the board. Native transaction failures leave both the denial and original cache intact.

Fresh gestures use the same native barrier, so a denial arriving before a local preparation commit blocks that new gesture. Existing unconfirmed originals remain recoverable; their close choices and historical acceptance keep their separate contracts. Restoring current access does not rewrite earlier source, actors or outcomes.
