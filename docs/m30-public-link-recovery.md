# M30 customer link issuance recovery

M30 remains in progress. This backend increment adds inspection and closure of an original customer-link issuance attempt. The owner interface, customer tracking pages, genuine phone-Auth commissioning and the remaining milestone acceptance stay open. GitHub workflows and Pages publication remain held. Each installation supplies its own backend and optional provider configuration; this work needs no new service account, maintainer phone or provider credential.

`create_public_link` still returns its random secret exactly once. Its original response and secret-free creation audit retain their format. A repeated creation ID cannot replace the secret. The capability now records the original creation event internally; existing grants are matched to their existing creation audits without changing those audits, token hashes or dates.

An authenticated owner or assigned manager can call `read_public_link_attempt` with the original link ID, creation event ID, kind and resource ID. The result reports `missing`, `issued`, `revoked`, `expired` or `closed`, with the original public link metadata and any closure's actual event, member and server time. It never returns a secret or hash. A changed event, resource, outlet or purpose cannot rebind an existing attempt. A missing result is an observation: a delayed create request might still arrive.

When the original secret is unavailable, `close_public_link_attempt` records a durable closure of that exact attempt. If issuance already committed, closure revokes that capability. If issuance has not committed, closure prevents the original link ID from being created later. Only after confirming closure should the interface offer a fresh link ID and creation event. It must never promise to recover a lost secret or silently issue a duplicate.

The closure response preserves the first accepted closure event, member and time on retries, including a retry by another authorized manager. An interface must distinguish observing that accepted closure from acceptance of its own later event. A `public_link.close_attempt` audit records the real closure; closing an absent attempt does not invent a creation or revocation event. A failed audit insert rolls back the closure and any revocation together.

All lifecycle functions derive the tenant and outlet from the actual order or khata account. They lock current membership, confirmed non-anonymous phone Auth and manager assignment, followed by the resource and a transaction advisory lock for that link ID. The original create, legacy revoke, inspection and closure paths use the same attempt lock; customer reads keep their existing budget/capability lock order. Lifecycle lock waits are bounded to two seconds. Fresh server time determines expiry and closure after waiting. These choices follow the [PostgreSQL locking guidance](https://www.postgresql.org/docs/17/explicit-locking.html) and [Supabase function guidance](https://supabase.com/docs/guides/database/functions).

A serialized per-member budget permits at most 100 recent closures in fifteen minutes before refusing another unknown attempt. Exact closure retries and closure of an existing capability remain available. Durable closures survive budget-window rollover so a much later request cannot reopen an old attempt. The private closure table forces RLS and grants no direct access to API roles. Public wrappers remain security invokers; private privileged functions pin an empty search path. No cleanup scheduler or provider setting is added.

The focused suite covers both issuance/closure orders for order and khata links, one-time secrets, original metadata and audits, scope changes, unassigned managers, staff and agent denial, current Auth restrictions, private grants, expiry, bounded unknown attempts and audit rollback. The migration also passes a native full-schema probe and 28 managed SQL-role checks inside a rolled-back transaction. Two actual concurrent managed transactions pass in both orders, with an overlapping advisory-lock waiter observed: issuance first is revoked by closure; closure first rejects delayed issuance. Neither outcome leaves an active orphan. All fixture rows are removed; temporary test Auth rows are deleted before their transactions commit. These are database fixtures with claimed test identities, not genuine signed-owner HTTP or phone-OTP acceptance. No fixture Auth account is retained and no provider request is made.

The owner UI must retain a credential-free journal scoped to the original installation, account, business, outlet and member. A returned secret may remain in memory only after validating its receipt and fresh scope. Reload or a lost response requires inspection and explicit closure before replacement. That interface is the next increment; the existing local and manual sharing paths remain available.
