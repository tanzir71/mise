# Owner publication and customer ordering — M33 in progress

The `publicOrders` preview connects an owner-approved shop snapshot to real customer order submission. A customer can save an original request, post it without an account and automatically open its own tracker. The existing WhatsApp and Copy paths remain available. [Recorded shop estimates](order-estimates.md) extend the tracker with explicit ranges and honest delay data. Full M33 still needs corner-shop price/swap acceptance and customer payment choices; it stays unchecked. The flag defaults off, the new public endpoint is undeployed and disabled by default, and GitHub workflows and Pages publication remain held.

An owner or assigned manager uses Shop link settings to publish the current, synced M20 snapshot. The installation supplies its own connection and phone sign-in; the control requests no maintainer account or credential. Publication checks the real current outlet and catalogue, records its original event and can be scoped to an explicit table. The browser saves its publication ID, event, public capability and source before HTTP. A lost reply can be checked with the same original publication rather than creating a replacement. Metadata pages list only the current authorized outlet's publication records, including publications from another device; they never recover raw secrets. Disable retains its original event through a lost reply and immediately blocks local sharing or replay of the publication. A confirmed, current reply is required before sharing a saved capability again.

Publishing confirms the approved link; it does not configure or enable the backend service. Each installation owns that separate configuration. Privileged keys stay on its backend. The shared ordering link contains only public shop data, a public API origin and the shop's ordering capability, with no publishable key, owner JWT, service key or tenant/member selector. The public capability is intended for customers to open; it grants no order-list, customer, khata or financial access. Customer contact is request data, not proof of phone ownership and not permission to charge an account. See [installation configuration](configure-services.md).

The existing `/app/s/` form keeps its unchanged 60,000-byte complete offline limit. The new `/app/o/` entry shares that form's source and template, and builds its own complete recovery bundle and worker cache. Compile-time separation removes the new ordering code from the legacy form; the new entry has a 75,000-byte bound. Both entries include their complete fonts and cache resources. The owner worker excludes both public paths, and the customer code imports no owner Auth or IndexedDB code. The new page's HTTPS/loopback connection policy permits its runtime installation endpoint without embedding any deployment identifier in the build. Both root and repository base paths remain supported.

Before HTTP, the customer journal saves and reads back the complete canonical intent, cryptographic tracking secret, derived original reference and all proposed record identities. A shared browser lock prevents competing tabs from replacing that original. An unconfirmed request must be retried, checked or closed before another is prepared. Closure is saved locally before HTTP, survives offline reload and blocks a delayed local submit. When the server already created the order, closure returns its actual receipt instead of claiming a cancellation. Server errors, timeouts, malformed responses and storage failures preserve the original and keep the message fallback available. A cached receipt alone never causes automatic navigation; an actual created outcome opens its purpose-bound tracker.

The public HTTP request has no account, API key, cookies, URL query credentials or referrer. It has fixed endpoints, strict input/output fields, complete response deadlines, size bounds, server budgets and a captcha-free honeypot. The complete original request remains inert data. Current catalogue selections keep their approved integer prices; text requests and unknown delivery fees stay unpriced. New orders record cash pending and create no sale or khata charge. The requested payment method remains source for the shop to review. The original message fallback includes the saved request reference so the shop can check it before adding another order.

An ordering link's displayed table is an assertion, checked against the actual server preparation before completion. It never chooses the stored table. A forged Table 9 display cannot create an order under a Table 4 grant. Successful table orders open their tracker automatically, and the tracker shows the table from its own scoped order record. The projection adds only that recorded label, preserving the previous capability, outlet scope, expiry, revocation, ledger behavior and execution grants. It adds no private address or phone, guessed arrival estimate, status history or payment confirmation. An entirely unpriced request has no misleading zero subtotal; a partial subtotal is labeled as priced items only. Literal note line breaks remain visible.
