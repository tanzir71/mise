# Retained payment originals and complete backups

Native schema 30 adds three separate stores for immutable original bases, original-node references and shared JSON values. Retention compares the reviewed complete native source with the current shop inside one transaction. A stale source or a quota failure retains every current financial record and rolls back all archive writes. The same frozen root is idempotent. These local originals contain evidence, never backend authorization or canonical money.

Each retained basis remains a complete, strictly validated schema-13 original. Current records and original records are validated independently; an original financial action is never rebuilt using newer canonical rows. The existing version-one original graph and its source table contract stay unchanged. Archive data is outside those source tables, so an original cannot recursively capture its own archive.

The ordinary backup controls now download and restore retained originals. A backup with no archive keeps format version 1, schema 13 and the same twenty-two domain tables. A backup containing originals uses explicit outer format version 2 with a checked current snapshot, original roots and a shared value graph. Existing current-snapshot readers reject that outer format instead of dropping its originals; the complete portable reader verifies both parts. Owner recovery and join backup actions also use the complete current portable export. An explicitly selected historical upload/source copy remains that particular original copy.

The shared representation uses typed nodes outside user data. Repeated values and canonical JSON strings share content addresses, then reconstruct the exact original strings before original-node hash and financial-history validation. NULs, lone UTF-16 surrogates, Bengali text, image data, source strings and all original note code units remain complete. Object keys such as __proto__ stay ordinary data. Missing/changed nodes, unreachable payloads, duplicate roots, wrong scope and oversized shared expansion fail before native mutation.

The physical file limit stays 50 MB. Each materialized current/original snapshot keeps its existing 50 MB limit. A complete archive also has a 200 MB aggregate original-snapshot validation budget and at most 512 original bases; capacity failure preserves all existing bases and never evicts one. The encoded file must fit its physical limit; nothing is truncated. The fixed 5,000-charge/million-code-unit corpus exercises three collections, original retention, native undo, shared export, cold restore and exact original financial lookup. Its measured wire and expanded sizes are recorded with the verification results.

Restore comparison includes both the selected and current archive roots. A newly retained original after preview requires a new review. Restoring current records, complete originals and operator state shares one native transaction, including rollback if original storage fails. A reviewed legacy file deliberately replaces the selected shop and clears its previous archive together with its domain records.

Legacy upload and canonical writers remain fenced from archived Payments, including when the separate current Payment table is empty. New retention is held behind a live binding until the full connected adapter is implemented. The paymentText preview remains off by default. Still required in M41: connected original transport/receipts, original-versus-canonical financial outcomes, native app outbox, historical initial registration without replaying money, and full canonical projection. This local archive facility is the retention boundary for that work.

Every installation configures its own hosting, backend, accounts, credentials, clocks, source labels and phone numbers. This work adds no provider or environment variable and needs no maintainer input. No hosted migration, service, workflow, publication, commissioning or tag is enabled. See the [verification record](payment-original-archive-verification.json) for the completed checks and exact scope.

Verification covers all 5,559 distinct unit cases across 293 files through the full run and corrected historical-fixture recheck, 49 browser cases per hosting path without skips/retries/flaky results, both builds and final lint/types. Astro checked 225 files with zero errors/warnings/hints. The complete three-original scale file measured 28,780,917 bytes against 55,781,689 bytes of expanded JSON, retaining all 5,000 charges, the million-code-unit note and original image data. No product markup/styles changed and no new visual comparison or hosted CI artifact was produced.
