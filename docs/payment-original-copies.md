# Private connected copies of payment originals

M41 can now transfer a complete original archive to an installation-owned backend, verify its full download, and recover a known copy into an empty private journal. This is transport groundwork. It does not install canonical records, authorize financial changes or enable the default-off payment preview. The ordinary domain schema, native schema 30, original graph version 1, legacy upload bytes and all existing upload/live-binding/canonical fences stay unchanged.

Every installation supplies its own hosting, backend URL, publishable key, phone sign-in and allowed origins through its existing setup/private backend environment. The new function uses only the existing SUPABASE_URL, MISE_PUBLISHABLE_API_KEY and MISE_ALLOWED_ORIGINS variables. It needs no administrator key. Journal connection bindings contain only account and destination hashes. Connection URLs, API keys and live session tokens are not recorded as journal configuration. The archived shop data stays complete, including its original source links and contacts. There is no maintainer configuration request or shared account.

The client strictly verifies current and original snapshots before preparing an immutable copy. Its private IndexedDB journal retains the exact manifest and content-addressed values before HTTP. Resuming checks which values the backend already has; unchanged values are shared within the same actual user, business and outlet. Large individual values travel as 144 KiB byte parts. Requests, responses and total fetch/body lifetimes are bounded. UTF-8 parts are reassembled before decoding, preserving full Bengali text, NULs, lone UTF-16 surrogates, original images and imported notes. Capacity, corruption and account changes retain all original records; there is no eviction or truncation.

The HTTP handler admits the actual caller before consuming a body. PostgreSQL rechecks the actual Auth user and live session on each operation, including expiry, sign-out, anonymous/deleted/banned users and verified phone status. A new write also locks the current active owner/manager and, for a manager, the actual outlet assignment. Editable user metadata supplies no authority. All operations forward the original caller JWT under the installation's publishable key; the Data API verifies that token. The platform JWT gate remains enabled as an additional boundary. See Supabase's [session revocation guidance](https://supabase.com/docs/guides/auth/sessions) and [authorization-header documentation](https://supabase.com/docs/guides/functions/auth-headers).

Five private forced-RLS tables deny direct grants to anonymous, authenticated and service roles. The narrowly scoped private definer has an empty search path; its public wrapper is an invoker callable only by authenticated users. Every new Auth/copy foreign key has a supporting index prefix. A per-account transaction lock serializes index, data-budget and completion changes. The protocol allows at most twenty pending copies, 512 copies in total, 1,638,400 aggregate declared node memberships and 512 MiB of retained node/part reservations per account. A copy declares at most 50 MiB of node bytes and 819,200 nodes. Each resumable verification step expands at most 512 queued values and records checked membership under the same lock. Partial membership cannot be downloaded. Completion checks all reachable counts/bytes and atomically publishes the immutable receipt. No partial copy receives a completion receipt.

A receipt explicitly says content-addressed-copy. It proves the declared bytes were stored, not that a historical financial claim is true. The server may store a structurally valid but semantically invalid graph supplied by its own authorized user; such a graph cannot pass the strict client archive/original/financial validators and grants no financial or membership authority. Real native execution and original-versus-canonical outcomes need their separate verified command path. Bounded parts keep the Edge Function away from materializing an entire archive; Supabase currently documents a [256 MB memory and two-second CPU limit](https://supabase.com/docs/guides/functions/limits).

The same actual account can inspect and recover its own completed historical copy after membership removal, while a new upload requires current permission. Sign-out and expired sessions still deny historical reads. Recovery requires a known original copy ID and the original business/outlet/actor scope; a new journal downloads and verifies the complete graph before retaining it locally. This does not replace current shop records. Copy discovery and user-facing retention controls belong to the remaining connected adapter.

Lost completion replies, native reloads and local receipt-write quota failures recover the original server receipt under the same ID. Journal lookups and receipt writes require the original destination/account identity. Callers must supply the current SDK account, connection and native-scope verifier; a no-op verifier is only a controlled test boundary. The production adapter remains gated until that live binding is integrated. An already completed copy cannot be rewritten. Local preparation rolls back on quota failure before transfer. Native original retention and restore also queue at most 512 inserts per batch inside their existing transaction. A later batch failure rolls back earlier batches and preserves current money. The chain uses [Dexie transaction-aware promises](https://dexie.org/docs/Dexie/Dexie.transaction%28%29), including the empty-archive path. A failed readback cannot mark a copy verified. Ordinary complete JSON export remains the manual/offline path.

Native invocation lookup also derives its constant companion ID once. A bounded calculation memo reuses SHA-256 only after serializing the complete current canonical input and matching the exact string. Its accounting limit is 32 MiB/16,384 entries; inputs above 128 KiB are hashed completely and not retained. This caches no mutable object, role, consent, validation result or permission. All financial/source checks and original digests remain unchanged. Independent Node crypto and arbitrary-JSON tests verify byte parity, mutation detection and bounds. The unchanged 5,000-entry offline browser workflow now fits its original 90-second deadline.

The exact deployment bundle and migration are verified locally with real PostgreSQL roles and the HTTP protocol. Hosted JWT signatures, managed Auth, network deployment and provider commissioning are not locally simulated acceptance. The CLI local advisor command currently cannot connect to a running local stack; the verification instead includes explicit local catalog/grant/index checks against all migrations. No hosted advisor was run. See the [verification record](payment-original-copies-verification.json) for exact results and limitations.

Final local checks pass lint/type checking, both production builds and 51 selected browser cases on each hosting path, with one browser worker and no retries or skipped cases. Unit coverage verifies 5,609 distinct cases across the initial full run and the final 363-case related run. The initial full run had two archive deadline failures; bounded native writes and exact digest calculation reuse were then checked against all affected payment/archive/backend cases. There was no single clean final full-suite invocation. Existing corpora, financial assertions and deadlines were preserved. The real transfer includes 5,000 charges, a complete million-code-unit note, a genuine collection and an original image. No new product markup or styles were added, and no hosted visual/CI acceptance is claimed.

M41 remains unchecked: native outbox integration, original-versus-canonical outcomes, initial historical registration without replaying money, complete canonical projection and end-to-end acceptance remain required. No workflow, CI upload, Pages publication, hosted SQL/function/service deployment, provider commissioning or tag is enabled by this increment.
