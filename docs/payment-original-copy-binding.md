# SDK-bound original-copy delivery

M41 now has a concrete controller for the complete retained original of the selected native shop. It derives its account and destination hashes from the actual phone SDK manager, project configuration and Auth storage namespace. It accepts no separately labelled identity, JWT supplier or copy-remote factory. The existing original-copy wire contract and backend SQL remain unchanged. This controller does not enable native payment sync or the payment preview; native outbox, outcome and canonical integration remain required.

Each installation supplies its own connection and phone sign-in through the existing settings. No maintainer account, phone, provider or credential is requested. The pinned Supabase client remains 2.119.0. Every HTTP request uses the existing verified command-account boundary: it checks the original target/account hashes, obtains fresh server-verified user information, binds the response to the uninterrupted SDK generation, and applies a 20-second total deadline and 256,000-byte response limit. `getSession()` supplies a token; the existing [getUser verification](https://supabase.com/docs/reference/javascript/auth-getuser) checks its actual user before a copy request and again before accepting its response. Server-side Auth session, role and outlet checks still run independently.

The controller compares the actual native setup, operator revision, account connection and cloud identity around every copy operation. Native read locks cover the separate private journal's prepare/receipt transaction, so a second connection cannot change the operator during that commit. Network calls hold no native transaction or read lock. Account/configuration changes, sign-out, explicit stop, invalid phone verification and native scope changes reject the result while preserving complete originals. A completed remote copy whose local acknowledgement was interrupted remains recoverable under its original ID.

Preparation reads the actual complete portable archive. Reopening an existing ID validates and returns that retained original instead of relabelling a newer export timestamp or current shop rows. Ordinary shop changes after preparation do not replace its source. A fresh SDK manager can reopen a saved original offline, but an offline stored identity grants no HTTP authority. Private journal writes roll back completely on quota failure. No connection URL, publishable key, JWT, refresh token or Auth UUID becomes journal configuration or ordinary backup data; archived shop source data remains complete.

Historical owner recovery is a separate capability. It binds the same actual SDK account to a strictly checked known original scope and exposes only readback/recovery. It needs no currently active native operator or backend membership, and it never installs current shop rows or grants a current role. The server still requires the original actual owner and live Auth session. New copy writes keep current native/SDK checks and server permissions.

The local verification exercises the actual SDK through a controlled Auth HTTP fixture, the real copy handler, local PostgreSQL roles and real native transactions. It includes changes after every transfer/download operation, actual concurrent native locking, lost acknowledgements, quota rollback, immutable preparation retries, membership removal and offline native reload. The fixture is not hosted JWT-signature or managed Auth acceptance. No schema, receipt, original graph, backup format, provider, environment variable or product markup/style changes are introduced.
