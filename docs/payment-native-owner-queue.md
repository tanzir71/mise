# Original payment queue controls

M41 remains in progress. The opt-in payment preview now shows saved native payment approvals in Sync settings and can explicitly continue their original shared queue through the actual phone SDK, original-copy service and native financial endpoint.

Each installation supplies its own backend connection and phone sign-in. No maintainer account, receiving number, provider credential or deployment identifier is supplied by the repository. Privileged service credentials remain in the installation's private backend environment. No hosted service, migration, workflow, release tag, CI artifact upload or Pages publication is enabled by this increment.

The queue distinguishes **Awaiting connected result**, **Original result saved**, **Needs original review** and **On this device**. An uncertain reply never means that money was not recorded. A saved result is historical evidence, not a claim about current money or a confirmed canonical cursor. Source and complete-backup links remain available.

**Pause sync and continue saved queue** continues only approvals already persisted on this device. It preserves original command IDs, complete source, original account/outlet scope and the global ordering of payment and ordinary shop actions. It does not approve a new payment. Backup-restored history cannot recreate outgoing approval; installed native views and local-only histories remain fenced.

Foreground delivery owns the same durable lease as background synchronization, while normal sync is paused. Live native scope, the actual SDK account and connection, lease ownership/expiry and cancellation are checked around HTTP and acknowledgement. Stop, scope withdrawal, a lost reply or local quota failure retain the original uncertain request for a later explicit retry. Reopening the controller uses the same private original-copy journal for that local database.

Normal synchronization remains paused after this operation. Native markers stay retained; no legacy receipt, canonical cursor or historical registration is fabricated. Current financial-context writes, explicit original-conflict resolution, historical registration, metadata-removal/scope recovery and complete M41 acceptance remain required. `paymentText` and `cloudSync` still default off.

Verification is recorded in [the queue verification record](payment-native-owner-queue-verification.json). The preceding complete 5,000-entry/million-character/image installation corpus and its unchanged deadlines are recorded separately in [native installation](payment-native-installation.md); this focused product increment does not claim a new full-suite or full-scale foreground qualification.

The queue uses the supplied M31 settings context: mobile M27 More and Desktop 14 Business data, with shared typography, outlined controls and status words. M41 provides no dedicated queue export. Reference differences are informational. Capture styling places the fixed navigation within the full-page image and clears focus after accessibility checks; it preserves the actual controls and warnings.

Browser verification uses the real built product, actual SDK, PostgreSQL roles and production HTTP handlers with a controlled synthetic Auth/HTTP boundary. Its existing v1 binding has no legacy private upload-review file, so the captures also show the existing upload-recovery warning. The warning stays visible.

The focused checks cover 105 distinct unit/guard cases, both production builds, 16 distinct browser cases per hosting path and 31 reference comparisons per path. Root coverage combines the complete affected baseline with a corrected five-case recheck; Pages passes the complete 16-case invocation. All five queue widths pass accessibility, overflow and offline-reload assertions. The verification record preserves initial failures and exact recheck scope. CI artifacts and publication remain held.
