The default-off Inbox preview now connects explicit browser consent, original-request recovery, the production service-worker handlers and authenticated current task targets. ## Enable and turn off

Open More › Notifications in the Inbox preview. Enable this browser through its explicit browser-permission gesture, then choose **Enable urgent alerts** separately. The second choice verifies the actual original phone account, native outlet/member, registered browser capability and installation readiness before saving a new consent intent. It becomes enabled only after its original server receipt is confirmed and the same current local choice remains active.

**Turn off urgent alerts** saves local No even while the first Enable is still waiting for configuration. It works offline and retains exact original withdrawals before HTTP. A late registration or inspection cannot override that choice. A failed native save reports that off was not saved and leaves the actual earlier preference intact; it never sends an unsaved withdrawal. The browser-wide Disable commits both purposes' local choices and original withdrawals in one private IndexedDB transaction.

If urgent originals are unreadable, browser-wide Disable preserves those bytes and saves the healthy base No. That base choice blocks both notification handlers and its original removal revokes the shared browser capability. An unreadable urgent record is not discarded or treated as a confirmed receipt.

Kitchen warning settings remain separate. The owner Inbox preview can configure notifications without enabling the kitchen preview flag. Existing kitchen notifications keep their original handler, consent and acknowledgement behavior. Hiding a preview is not a substitute for withdrawing its notification choice through these controls.

Add task by hand includes an unchecked **Urgent · notify subscribed devices** choice. Only a person's explicit choice sets this priority; words or instructions inside the source do not. Observed unmatched payments retain their own actual urgent source workflow. A human task choice records task/audit metadata, without executing source text, sending a reply, posting a payment or changing an order.

## Original account recovery

**Earlier urgent alert setups** opens outside native outlet selection. It can turn off a saved setup locally, offer a complete private original copy, inspect an original registration result and confirm that original's withdrawals. It exposes no fresh consent, task-read, native selection or membership method. An immutable registration result stays historical when recovered here and cannot enable presentation.

Recovery borrows an existing SDK view only when its actual original account and backend target match. Otherwise it uses a separate recovery sign-in namespace. The recovery connection also has its own private setting; choosing it does not replace the app's current connection. Disposing a recovery view preserves other signed-in SDK views. Another phone, backend or selected operator cannot acquire the original request's authority. The original phone can still inspect and withdraw after assignment removal, while current task access remains denied.

The original copy contains consent metadata and exact request/receipt identities, without backend URLs, phone tokens, provider credentials, push endpoints or browser encryption keys. Downloading it removes nothing. Pending originals are retained and never evicted; this increment does not add completed-history removal or change the groundwork's reserved withdrawal capacity.

## Actual service worker and target screen

The built worker dispatches the two strict notice types to separate kitchen and urgent handlers using the actual native database, desk cache and PushManager ports. Generic notifications contain closed routing IDs only. Source text, money, credentials and caller-chosen URLs cannot become notification content or destinations. An owned recheck message closes only notices whose own original choice is no longer authorized.

Clicking opens a fixed same-origin Inbox URL under the installed app base. The target screen rechecks original consent, current native scope, actual browser subscription and fresh phone authorization before and after HTTP. The backend additionally requires current rights and an actual delivery attempt. A mismatched outlet offers deliberate operator selection; it never changes the native selection itself. Invalid, withdrawn or unavailable alerts offer Inbox and setup links without exposing the task.

The server's current task and generation remain separate from the original alert. Resolved or reopened alerts explain their current state. Human tasks open the existing Inbox with its current inline controls and source fingerprints. Payment targets open the existing guarded payment-source review. Each action still performs its own current source and authorization checks. A worker refresh wakes current Inbox reads; a late response, failed clipboard or revoked scope cannot restore an earlier private source.
