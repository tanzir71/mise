# Staff quantity requests and original recovery

The paired-screen quantity backend is verified. It supports used, received, waste and physical count requests, complete batches of up to 1,000 lines, and undo of the current member's own recorded movements. Every request first produces a current comparison; confirmation is a separate operation. The [native follow-up](staff-stock-native.md) supplies the journal and controller; the shared-screen interface is still required. M34 remains unchecked. The new service is undeployed and disabled by default; workflows and publication remain held.

## Authority and current review

The outlet's actual Team **Update stock** choice grants eligible enrolled-device/PIN members quantity capabilities. Existing individual denials still apply separately to reads, adjustments and undo. Riders and kitchen members using counter attendance retain their attendance-only boundary. Removing stock read also removes the two quantity capabilities. This grants no catalogue, supplier, purchasing, payment or owner/manager sign-in authority.

The service derives its fixed RPC arguments from the complete original request. SQL verifies the actual device, current PIN, original member/session, outlet assignment, activity, role, mode and real-clock expiry. The original session remains identifiable when a later PIN reviews the same person's saved request. No owner JWT, owner stock ticket or invented owner identity is used for a staff operation. The existing owner stock paths retain their own admission.

Prepare reads the actual current quantities without changing stock. A separate confirmation binds the private review token, complete source hash and backend comparison hash. Absolute counts use the predecessor explicitly shown in this comparison; the original count, physical occurrence time and allocated IDs remain retained. Receipts record the actual reviewed predecessor and result for every line. Relative changes use integer-thousandth arithmetic and never produce a negative amount. Stale comparisons require another review, including after Team No then Yes. The comparison snapshot includes current Team/member state and the latest actual owner movement withdrawal. A new withdrawal invalidates an older comparison; a fresh comparison identifies the affected items for explicit review.

Undo checks the actual stored own-member receipt and movement, once within 24 hours and before a later active physical count. A caller-edited parent receipt cannot authorize somebody else's movement. Undo records its own movement and audit and preserves the original batch and parent identities; it does not erase history.

## Complete source and recovery

The original request retains its full selected quantity projection, literal labels, aliases, units, note, original PIN scope and native screen revision. The existing 50 MiB source budget and million-character imported fields remain supported without clipping. The service checks real enrollment and a shared device/server-minute budget before reading a large body. Compact unit hashes avoid copying large units into a second privileged parameter. Actual database metadata remains authoritative for the resulting movement and complete before/after audit. Native JSON preserves NUL and surrogate source without decoding whole source-bearing values as JSONB.

Small outcome responses bind the hash of the complete retained original instead of echoing a second escaped copy of all its labels. The backend still stores and compares the exact complete original text. Inspection under the same member's later PIN can recover a committed receipt after its first reply was lost. Confirmation retries inspect first and never apply the movement twice. Inspection and closure need own-original identity, separately from current work permission.

Closing an unconfirmed request records that decision and reserves every newly allocated movement, batch and audit ID. It creates no stock movement or synthetic count. The original stock item remains usable. Existing owner inserts and imports encounter the same closed-ID fence, and a late prepared confirmation cannot revive the request. A genuinely applied request remains applied when inspected or closed; withdrawal cannot relabel a physical movement as unperformed. Expiry during confirmation rolls the whole transaction back, including quantities, movements, audits and receipts.

Structural parsing alone does not authenticate a receipt or authorize a quantity change. The upcoming native writer must also require the actual live HTTP response proof, exact saved original, current enrollment and local comparison. Prepared tokens must remain ephemeral; serialized access or review data must never restore write authority. The stock journal needs its own native schema upgrade and must preserve the existing state, kitchen and attendance stores. The owner workspace is not the shared-screen store.

## Installation configuration

Each installation owns hosting, its backend connection, device pairing, member PINs, exact `MISE_ALLOWED_ORIGINS` and the private `MISE_SERVICE_API_KEY`. There is no additional provider account, receiving number, OTP or maintainer credential for this feature. Empty templates contain no project, organization or credential value.

Keep both `MISE_STAFF_STOCK_ENABLED` and `MISE_STAFF_STOCK_WRITES_ENABLED` false until the installation's intended stock preview is ready. The separate `staff-stock-actions` write service requires both choices. `MISE_STAFF_STOCK_REQUESTS_PER_MINUTE` remains optional, accepts 1–60,000 and defaults to 600; reads and body admissions share that device's server-minute budget across PIN sessions. Deploy the matching app, shared-screen functions and migrations together so their closed capability parsers agree. Supabase documents [function authorization headers](https://supabase.com/docs/guides/functions/auth-headers) and [explicit database function privileges](https://supabase.com/docs/guides/database/functions).

Continue using the existing owner/assigned-manager stock flow or tell the manager the change by hand while the staff interface is unfinished. The native flow must retain complete offline originals, explicit closure, comparison and receipt recovery, plus usable manual copy/handoff controls. Configuring a backend does not itself finish or commission that interface.
