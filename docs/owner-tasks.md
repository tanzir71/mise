# Inbox tasks and original human choices — in progress

The default-off `ownerTasks` preview now connects the general task protocol, backend and native request journal to Inbox and Questions for you. Payment-source matching and general urgent push delivery remain to be built. Existing kitchen notifications keep their current scope. No new provider account, phone number or maintainer credential is required for these task APIs; each installation uses its own connection and verified phone sign-in.

An installer can opt in with `?flags=ownerTasks`; this also makes the installation's Sync setup available. The preview reads actual recorded tasks, including real customer khata questions and kitchen sources. Add task by hand records a person's question, message or check with empty fields. It creates no sample task or agent/provider activity. Waiting and Resolved preserve their complete counts. The separate Questions view counts only its selected questions. Existing shared text/images remain accessible separately when `shareTarget` is enabled, and kitchen warnings are not counted twice.

The interface checks current tasks every five seconds while visible and offers manual refresh. A failed refresh retains the last complete list read-only. A server access denial removes the private list and its open detail. The source sheet displays literal customer text and a human reply. Copy message has a complete, selectable fallback if clipboard access is denied. Check WhatsApp recipient reads the actual task again before offering its recorded E.164 destination. Opening WhatsApp does not send or confirm the reply. I sent it is a separate, explicit statement. A source target opens only an available native order or the exact customer/account/entry in the selected outlet and currency; it never silently switches accounts.

An owner or currently assigned manager can read complete, versioned task pages for their outlet. Counts come from the entire selected list. Cursor ties, source changes and contact/author changes are checked so an interrupted list cannot look complete. Each response uses one SQL snapshot for rows, source projections, counts and version. The native reader follows every page and accepts a list only after its last cursor, with the expected complete counts and no repeated rows. It retains no persistent dashboard authority.

Manual tasks have explicit decision, message or check modes. Allow and No record a human decision about the request; they do not execute a customer message, alter an order or write money. Reply myself keeps the task waiting. I sent it records the person's explicit statement and complete reply; it does not claim provider delivery. Check and reopen choices are also audited. Undo checks the actual last choice and source before restoring the prior task state. No task choice changes sales, balances, stock, attendance or provider status.

Real customer khata questions retain their original customer/account/entry target and literal text. Their manual replies can resolve the task without changing the ledger or deadline. Real kitchen alarms retain their canonical order target and actual Got it lifecycle; generic task choices cannot close them. Unknown source actions remain read-only. Payment targets are reserved as read-only source references until their actual matching workflow is connected.

Every original contains its full task image, source fingerprint, phone-account scope, unique action/event identities and chosen reply. The server compares the real current source before a new choice. A per-task revision prevents reuse of a personal action ID in another account from restoring an older fingerprint or confusing undo. Exact retries recover the same receipt. Inspection and closure of one's own original remain available after outlet access removal, without granting a fresh task read. A closed unknown original fences a later submission and creates no public task or audit. New unknown personal closures are bounded at 1,000 per server day; exact recovery and genuine new work keep their existing paths.

The native journal saves before HTTP and before trying an explicit closure. It uses the original account/connection hashes and native business/outlet/member, stores no token, API URL, publishable key or browser/provider capability, and does not enter the shop backup. Its 200-original and 8 MiB bounds retain earlier work rather than evicting it. Lost replies, quota errors, competing writers, changed accounts, native selections and older-role originals keep their original scope. A serialized or modified task has no live response proof and cannot prepare a choice. The original-request panel blocks a replacement while the actual result is unconfirmed. Check original result, Retry original request and Close original request always retain that same source and identity. A saved closure is visible before its network request.

Offline initialization uses a separate, in-memory local identity proof tied to the actual stored Auth SDK session. It contains no JWT and grants no operator, member or HTTP authority. Damaged/mismatched local claims, serialization, another SDK instance, sign-out, disposal and changed account/native scope cannot transfer a proof. Fresh server authorization remains mandatory before sending or accepting a task response. A real browser test reloads the installed PWA offline, reopens the same journal, saves its closure, reloads again, reconnects and confirms that original closure without an OTP. Physical installed-device acceptance and a separate personal cleanup interface for originals from unavailable native outlets remain open.

Literal fields stay encoded through the protocol and audit so Bangla, escaped NUL and surrogate data survive unchanged. Only closed routing fields are inspected for khata source indexing. Customer text and raw action objects never select an executable command or arbitrary application URL.

The installation proof uses actual Core setup and task originals, verifies real PostgreSQL owner/manager access, decisions, undo, closure, historical recovery, helper/table denial and unchanged money, then rolls back all synthetic records. The same 45 assertions pass locally and against a private installation backend. All ten new function bodies match the applied migration, all 470 previous function definitions are preserved, and all 112 application tables force row-level security. No SMS, messaging or push request is made. The [backend verification record](owner-tasks-verification.json) retains exact evidence and source hashes for the preceding engineering checkpoint. This interface increment changes no database migration, Edge function or scheduler.
