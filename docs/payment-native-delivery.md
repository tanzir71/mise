# Native payment delivery and session-bound outcomes

M41 now delivers the exact connected native payment invocation through the existing native backend, after storing and strictly reading back its complete independent original copy. It retains separate immutable copy and financial outcome receipts in the private native journal. Delivery never repeats local money, rewrites the original invocation or substitutes newer current rows for the source. The payment preview remains default off and M41 remains unchecked.

`createNativePaymentOutboxSession` obtains its account, destination and operator from the actual phone SDK and native scope. It exposes review, delivery and stop operations; callers cannot supply separate identity labels, arbitrary JWT suppliers or remote factories. The controller rechecks the actual SDK/configuration/native scope around HTTP and private writes, uses bounded requests, and aborts on account/destination changes. Every new drain obtains fresh verified responses, including idempotent recovery of saved outcomes. Serialized receipts never authorize delivery.

The sender preserves the common legacy/native sequence. Earlier Inbox metadata and image delivery precede the native source; later legacy commands wait for the genuine original-copy and financial receipts of every action in the native group. An ephemeral runtime proof rechecks the actual marker, journal, receipts and live account before passing a native marker. The marker remains retained version one, with no fabricated legacy commands, receipts or canonical acceptance. Unknown retained work still blocks the queue. Genuine HTTP 409 observations are stored separately from original intent and never silently rebase money.

A lost reply or private acknowledgement quota failure leaves the exact original available. A later controller retrieves the backend's immutable outcome before allowing later commands to proceed. Independent source seals and strict full copy readback preserve complete ledger/image/text evidence even when current rows advance. The sender verifies the exact original invocation/event in the copied basis before requesting the financial result.

The CLI-created migration adds one private, forced-RLS ticket/session relation with no client or service-role table grants. Existing admission, preparation and service completion bodies are replaced in place, retaining their protected OIDs, grants and financial algorithm. They correlate the actual JWT session ID with a live session belonging to the confirmed, non-anonymous phone user, checking deletion, banning and expiry as well as existing role/outlet authority. This follows [Supabase's session guidance](https://supabase.com/docs/guides/auth/sessions). Completion rechecks the captured preparing session before and after the actual financial writes; expiry during a write rolls back the entire transaction. Revoked or old unbound tickets cannot finish. A fresh verified session of the same user may retrieve an already completed original outcome without reposting money. The relation deliberately has no foreign key to Auth sessions, so pending tickets cannot prevent logout.

Native schema 31, ordinary schema 13, original graph 1, copy wire 1, portable archive 2 and native command/receipt version 1 remain unchanged. No environment variable, provider account or maintainer credential is introduced. Each installation owns hosting, backend connection, service credentials, phone numbers, source labels and clocks. Privileged credentials remain server-side; existing manual/offline paths remain usable.
