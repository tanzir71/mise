# Native payment download in the shared snapshot

M41 now captures native payment observations, literal audit history and original backend outcomes in the same immutable transaction stream as their genuine financial rows. The existing bounded sync pages select all of them with the same PostgreSQL snapshot and 64-bit change ordinals. A later undo cannot mix a newer native result into an older financial window. This implements native download and staging; complete canonical installation remains fenced and M41 remains unchecked.

The three explicit projections are `native_payments`, `native_payment_events` and `native_payment_actions`. They expose scoped original JSON strings, actual invocation/request hashes and native outcome receipts. They omit Auth UUIDs, write tickets, service credentials and private member-cache columns. Clients validate complete fragment hashes, exact column sets, scope, native row shapes, invocation identity and outcome consistency before sealing the download. These row checks do not replace original financial/history validation or grant write authority.

The CLI-created migration adds two private typed member-reference columns and four invoker-only helpers. Native writers already run inside protected definer functions, so capture needs no additional privileged function or client table grant. Literal JSON stays text: the existing opaque parser extracts only a public member ID once during a native write, and indexed private columns support historical profile lookup. Ordinary PostgreSQL JSON field extraction rejected unrelated NUL/surrogate source in the first integration test; the corrected path preserves those values and the complete original strings. Historical references retain names/roles without inventing membership, phone access or active authority.

All native capture runs in the financial transaction. A failure after money insertion rolls back money, audits, native outcome and projected bytes together; an original retry records once. Existing native data is backfilled without executing an invocation or reposting cash, and the migration rotates the feed epoch so an older cached window cannot claim a complete new baseline. Existing financial routines and native child identities remain unchanged.

Native windows require the actual live Auth session before body consumption and before/after preparation and fresh or cached page reads. The original membership/user locking order is retained before acquiring the extra session lease. Revocation rejects cached data, and expiry during actual page persistence rolls its bytes and progress back. Legacy-only streams retain their existing behavior. Snapshot visibility follows [PostgreSQL 17's transaction/snapshot functions](https://www.postgresql.org/docs/17/functions-info.html#FUNCTIONS-PG-SNAPSHOT), rather than treating the largest ordinal or a wall clock as a commit cursor.

The existing version-one fragment/window/cursor envelopes stay unchanged, with a strict extended table vocabulary. The exact previous production reader is frozen as a SHA-256 checked test fixture and rejects every native fragment before accepting progress. A path-specific LF rule preserves that fixture across checkouts. Native outer records have explicit limits before full allocation: twice the original 50 MiB source bound plus 4 KiB, or twice the 256,000-byte invocation bound plus 8 KiB for outcomes. Existing legacy record limits and page budgets remain unchanged. Limits reject incomplete data rather than truncating originals.

Actual SDK/HTTP/SQL tests cover account isolation, lost cached replies, server-snapshot changes, upgrade/backfill, original undo, private privileges, tampering, tombstones and native record bounds. The unchanged 5,000-charge/million-code-unit/image corpus crosses real native delivery and the same-window feed with one collection, 10,037 records and 145 pages; every original charge and literal note is compared. Browser tests lose an actual cached-page response, reload and recover verified native records while the source still has one payment and the download database has no domain writes. This is local PGlite/restricted-role and controlled Auth integration evidence; managed JWT-signature, hosted database/provider and physical-device acceptance are not claimed. Exact results and corrections are in the [verification record](payment-native-feed-verification.json).

Final local verification passes lint, strict types (230 Astro files), all 5,716 unit cases across 298 files, both production builds and all 59 selected browser cases per hosting path, with one browser worker, no retries and no final failures, skips or flaky results. The initial Pages run passed 57 and failed two: an existing history test opened its disclosure before the saved revision remounted it, and the unchanged full ledger case reached its existing 90-second deadline. Two waits for the actual Link removed confirmation correct the history fixtures; the complete browser selections then pass on both bases with every original assertion, corpus and deadline retained. Production/unit source bytes remain exactly those qualified by the full unit run. The verification record preserves both initial failures and the complete final rechecks.
