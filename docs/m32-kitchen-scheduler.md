# M32 coordinated kitchen scheduling — in progress

The [later live timing checkpoint](m32-kitchen-timing.md) commissions Cron/Net, corrects the Vault parameter binding and verifies actual two-minute timing, disable/resume and rollback recovery. The results below describe the preceding scheduler delivery; its extension and activation status are historical.

The scheduler connects due order inspection and desk notification delivery in one internal invocation. A private SQL dispatcher checks bounded due work every second when explicitly enabled. Idle ticks enqueue no HTTP request. The migration installs disabled and needs no extension, job or credential to apply.

The coordinated worker starts any already-ready deliveries while inspecting independent orders. Each genuine inspection result wakes the same delivery pump, so a raised task can reach transport before a later unrelated inspection finishes. Both workers stop starting additional work at a shared ten-second deadline. Existing SQL authorization, original-content checks, recipient selection and twenty-second delivery leases remain authoritative. No request can choose an order, clock, scope, message or recipient.

Failed inspections keep their original watch due. A separate private retry records its original version and source stamp, with delays from one second up to sixty seconds. This prevents an older task from being delivered before changed order content has been inspected. A real version/progress change clears the old retry; a late failed result cannot postpone newer content. Ready tasks in other scopes remain eligible.

A bounded signature lets genuinely fresh work bypass an older transport's backoff. Requests are enqueued at most once per second, with a short cooldown for unchanged work and bounded transport retries. Queue insertion and dispatch metadata commit or roll back together. The unlogged extension queue is transport state; original alarm watches, tasks and delivery ledgers provide recovery after transport loss. Authentication/configuration failures retain original work and stop transport rather than claiming delivery.

Actual Got it closes the task and cancels unsent delivery. If a provider has already accepted an in-flight request, that real outcome remains history and never reopens the task. An in-flight failure after Got it is cancelled without scheduling another send. Provider acceptance is not proof that the browser displayed a notification, and transport retries do not promise exactly-once delivery.

## Private configuration and provisioning

`supabase/ops/kitchen-scheduler-dependencies.sql` is a separate privileged setup script. It installs Cron/Net and the standard pgcrypto implementation only when explicitly executed, validates their expected APIs and creates no job or credential. Existing uses, trusted SQL login roles and actual Data API exclusion of protected schemas must be checked before managed provisioning. It is not part of the all-migration local fixture.

Actual runtime configuration belongs in ignored private input and the server secret manager. Vault holds a closed URL configuration document and the independent worker key. The private control function takes their UUID references; client and service roles cannot execute it or read its state/configuration helpers. Before enabling, it validates the actual extension APIs, NOLOGIN API roles, Vault read permissions and closed configuration shape. The network request needs no API key because this internal function uses its own authorization with platform JWT verification disabled.

The named Cron job stores only `select private.dispatch_kitchen_work()`. No URL, key or request body is present in its command. An unrelated job with the same name is refused rather than overwritten. Disable removes only the owned job, preserves original application work and retains the private references for explicit recovery. Owner notification endpoints retain their phone JWT verification.

The managed dependency probe confirmed the documented [platform constraint on network queue access](https://supabase.com/kb/troubleshooting/revoking-access-to-pg_net-objects-has-no-effect-0bbc16): tenant revocations do not remove Supabase-owned default grants. Both empty probe extensions were removed afterward, with no job, credential or HTTP request created. The implementation therefore makes no claim that those grants were removed. Anyone trusted with direct SQL access can inspect the target URL and short-lived proof in the queue. Protected-schema API exposure must be verified separately; NOLOGIN metadata alone cannot prove that boundary.

Dispatch signs the exact nonce, issue time and bounded batch size with native pgcrypto HMAC-SHA256. Web Crypto verifies the proof before any SQL request; the worker then consumes that exact private grant once, checking the enabled scheduler revision and fresh post-lock expiry. Proofs expire after sixty seconds, with five seconds of clock tolerance. Replays, changed batches, missing grants, Disable and reconfiguration cannot start another inspection. A bounded cleanup retires expired grants. Neither the reusable worker key nor an API key enters Net headers, bodies or Cron metadata. Ordinary alarm/push handlers retain their independent private-key checks for internal in-memory calls.

Scheduling follows the documented [Cron sub-minute interval](https://supabase.com/docs/guides/cron/quickstart), [Cron/Net/Vault pattern](https://supabase.com/docs/guides/functions/schedule-functions) and [transactional Net queue behavior](https://supabase.com/docs/guides/database/extensions/pg_net). The installed managed APIs and permissions still need separate verification.

## Verification and remaining acceptance

A clearly marked test-only Cron/Net/Vault adapter models committed queue rows and permissions, including platform-style PUBLIC queue access; it performs no background scheduling, Vault encryption, network delivery or provider commissioning. Only the provider HTTP response and unavailable extension APIs are synthetic.

All 45 dedicated checks pass: 26 SQL/coordinator cases, eleven independent Node/Web Crypto authorization cases and eight packaged-runtime cases. They cover idle ticks, denied private access, unsafe API login/Vault configuration, job-name collisions, transactional rollback, failure backoff, fresh work, real encrypted dispatch, changed-content barriers, timely independent work, shared deadlines, accepted/failed in-flight responses after Got it, single-use concurrent replay, missing grants, expiry, changed batches and configuration rotation. Packaged-runtime checks load the reviewed pinned encryption dependency and reject missing configuration before SQL.

Both production base paths pass; all 61 compiled-root browser cases pass in 2.3 minutes and all 545 Pages browser cases pass in 23.5 minutes. This increment changes no UI layout; earlier visual captures remain historical evidence, with no new visual comparison claimed.
