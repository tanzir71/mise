# M30 customer capability reads

M30 remains in progress. Customer tracking and khata pages belong to M33 and M35 and are not enabled by this backend increment. GitHub workflows and Pages publication remain held. Each installation supplies its existing backend connection and server key; no new account, credential or maintainer phone is required.

The `public-read` Edge Function accepts a bounded JSON POST containing `kind` and a single 43-character capability `token`. A khata read may also contain a safe-integer `afterSequence` and `pageSize` from 1 to 100. Order reads do not accept paging. Extra fields, resource IDs, caller-selected clocks or limits are rejected. Tokens travel in the request body; query parameters are rejected. Customer reads need no account or owner JWT. The unguessable, purpose-bound capability remains the authority.

Only the fixed, service-only `read_public_capability` RPC is reachable from the transport. The earlier direct order/khata reader grants are revoked from every API role, so calling a legacy RPC cannot bypass the budget. Issuing and revoking links retain their original live owner/assigned-manager authorization, identities, expiry and secret-free audits.

The SQL transaction reserves a fixed installation-wide budget before looking up the capability, then a per-link budget under the capability row lock. Defaults are 3,000 and 60 reads per server UTC minute. The installer may set `MISE_PUBLIC_READS_PER_MINUTE` and `MISE_PUBLIC_LINK_READS_PER_MINUTE` to integers from 1 to 60,000 in its private backend environment. Empty settings use the defaults; invalid settings fail closed. These numeric settings are not credentials. Browser input cannot override them.

Unknown tokens consume the installation budget without allocating rows for random request IDs or retaining raw IP addresses. One fixed budget row and two private capability counters need no scheduled cleanup or new paid service. All reads lock the fixed budget before the capability; revocation locks only the capability. Lock waits are bounded to two seconds. Fresh server time governs admission and expiry, including after a lock wait. No client clock, forwarded IP header or customer-provided identity controls admission.

Unknown, wrong-purpose, expired and revoked links return the same generic 404. A completed revocation is visible on the next read, including when that link's own budget was exhausted. Limited reads return generic 429 JSON and a bounded `Retry-After` from 1 to 60 seconds; backend failures return generic 503 JSON. Every response is uncached, uses a no-referrer policy and disables content sniffing. Exact configured origins govern CORS; preflights and rejected input do not read shop data.

The response copies only customer-approved fields. Orders include their tracking status, exact item lines, prices, currency, original schedule and payment status. Khata includes the approved customer name, exact current balance and a bounded ledger page. Merchant notes, captured source messages, customer phone/address, staff identities, credit limits, internal payment details and audit records are excluded. Serialized SQL literals are decoded without trimming or Unicode normalization. Integer money, original quantities and complete 200-line orders remain intact; malformed totals, duplicate line identities and corrupt ledger cursors fail closed.

The backend request is fixed to one RPC, uses only its server `apikey`, rejects redirects and bounds both the full response and its five-second lifetime. The service key never enters the customer response. Read attempts change only private budget counters, preserving original orders, sales, khata and audits. A ledger that cannot be represented safely returns unavailable while retaining its reservation; a projection failure cannot roll back the budget and reopen unlimited failed reads.
