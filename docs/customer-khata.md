# Customer's own khata

M35 is in progress behind the default-off `customerKhata` and `customerLinks` flags. `/app/k/<token>` shows the actual customer's balance, entries, recorders and times at that shop. The separately disabled `/public/khata` endpoint remains undeployed. Workflows and public publication remain held. Each installation owns its hosting, backend connection, receiving accounts and private service configuration; no maintainer account, key, phone number or verification code is needed.

The backend derives the account, customer, business and outlet from the actual khata capability. The request format rejects additional scope or payment fields. The ledger excludes private contact details, addresses, account limits and other customers. Sequence pages contain up to 50 actual entries and preserve the total balance. Revocation and the actual expiry clock block fresh reads and new requests. Historical receipts acknowledge only the complete original submitted with that same capability.

Wallet accounts start empty. The owner configures their public receiving accounts in Settings › Shop link › Payments. Customers see them only when their ledger currency matches the current outlet currency. Pay rechecks the current target and positive balance before opening the wallet directly. Copy number, selectable text when the clipboard fails, and a separate manual handoff confirmation remain available. Opening another app records no payment; the shop records the actual collection.

Ask for more time and Question this entry create genuine canonical owner tasks and system audits. Customer text stays literal, including Bangla and imported JSON text, and cannot execute instructions, change money or extend a deadline. Entry questions must reference an actual entry in this customer's account. The task, audit and exact original receipt commit together. A capability that expires while the write is waiting rolls them all back.

The customer's native journal is isolated from owner Auth, the shop database and other customer links. It saves the complete original before HTTP and never caches the ledger or raw token. Lost replies retain the same identifiers for inspection or explicit retry. Closing an unfinished request is saved before HTTP, including while offline, so a later delayed submit cannot create a task. Storage failure blocks a new request while preserving fresh read-only data and manual copy. Journals and server receipts retain their first 200 actions rather than evicting earlier originals. Route changes and late replies cannot attach results to a different customer.
