# M32 desk notifications — in progress

The local notification worker now expands a kitchen alarm into durable deliveries for the eligible desks registered when that alarm generation is prepared. Each delivery retains the original task, generation and subscription. No-recipient expansion is recorded as complete without claiming a send. The worker claims a twenty-second lease, checks the current phone account and outlet assignment, and allows at most eight attempts with bounded backoff.

Claiming also waits for the alarm worker to inspect any queued order or settings change. This prevents an older content task from being sent while a newer genuine Got it is awaiting that inspection. A later revision that keeps the same preparation content can resume the original task without changing its generation or source binding.

A genuine Got it cancels unsent deliveries in its existing transaction. An already in-flight provider result remains transport history if the task closes meanwhile; it never reopens the task. Lost finish replies do not resend a recorded result. An unconfirmed provider request can be retried with the same recipient and task topic, so delivery remains at least once rather than an exactly-once claim.

The owner endpoint forwards the original phone JWT with the publishable API key. Platform JWT verification stays enabled: the user token goes in `Authorization`, and the publishable key goes in `apikey`, following the current [Supabase authorization-header guidance](https://supabase.com/docs/guides/functions/auth-headers). SQL resolves the actual member, business and assigned outlet; editable JWT metadata supplies no authority. Configuration returns only that scoped context and the runtime VAPID public key. Registration and cleanup return closed metadata without endpoint, browser encryption keys or Auth UUID. The original account can retire its own capability after assignment removal, and cleanup remains available when VAPID configuration is unavailable.

A personal withdrawal is durable even if the earlier registration has not reached SQL yet. Registration and withdrawal serialize on the original account/setup identity, so a late original registration cannot undo a later Disable. Another phone account cannot pre-close that setup. Exact withdrawal retries retain the original event; a never-created setup has a private personal audit record without inventing a shop/member event. New unknown withdrawals are bounded per phone account per day; existing closures never expire, retries consume no new slot and owned-subscription cleanup remains available.

Subscription capabilities and delivery ledgers are private forced-RLS tables without direct client or service-role table grants. Public audit contains identifiers and genuine outcomes, with no endpoint, browser keys or VAPID values. The delivery worker has its own internal credential check, rejects browser origins, reports counts only and uses the existing encrypted sender. Its only external runtime import is pinned `npm:web-push@4.0.0`; the owner endpoint has no external runtime import and requires platform JWT verification.

## Complete task reads and private browser state

The task reader now has versioned `(dueAt, id)` pages. Task mutations and warning-settings mutations both advance the outlet version, including a settings-only change that leaves every task open. Each stable database read checks the actual current phone account and assignment. A changed version or revoked assignment rejects continuation instead of producing a partial result that looks complete.

The browser transport follows every cursor under the original account and connection. It accepts only the original outlet/member/role, matching version and settings, advancing rows and closed Open order/Copy actions. An interrupted, repeated or empty continuation is rejected. The result becomes a complete list only after the final page. Warning changes and subscription actions capture their original IDs and values before asynchronous authorization.

The private `mise.desk.v1:<base>` IndexedDB database holds scope fingerprints, subscription metadata and complete task projections. It is separate from the shop database and its unchanged explicit backup table list. It stores no owner JWT, backend URL/key, endpoint or browser encryption material. A runtime HTTP proof binds each activation or update to the actual original account hash, connection target, scoped member and exact verified response. Serializing a response cannot recreate that proof, and editing a verified task array cannot manufacture trusted absence. Subscription absence results retain their original target ID before they can clear that device's metadata.

Profile and active-pointer updates share a transaction. Stale writers, partial results, older versions and changed account/connection proofs retain the previous verified data. Switching profiles disables the earlier local notification presentation. Local sign-out can retire presentation without a network token, while retaining the original metadata and cached source; a late cleanup cannot retire a newer account.

Private database version 2 adds an original-operation journal while preserving version 1 profiles and pointers. Registration and warning changes save their original event, scope and inputs before HTTP. Only canonical subscription and application-key hashes enter the registration journal; retries recover the actual capability from PushManager and refuse a replacement endpoint or key. An explicit Disable atomically mutes this desk and journals withdrawals for every setup that might have reached SQL, while keeping the complete cached Inbox. Withdrawals precede registration retries, and a withdrawn setup is never replayed.

Only the actual original mutation receipt can confirm an operation. A read reporting absence, an unrelated event or a serialized receipt cannot close it. An inactive original account may retain its genuine outcome without changing the current account. Enabling requires the original active-pointer revision, a native scope guard and the latest unwithdrawn registration choice. Late original outcomes cannot replace a newer subscription or undo Disable; metadata-only refreshes cannot bypass the journal. Warning receipts remain history until a fresh exhaustive task read supplies the corresponding task/settings projection. Browser controls and delivery workers still need to consume this foundation.
