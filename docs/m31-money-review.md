# M31 · Counter and khata financial review

An offline counter or khata action can be rejected when the current shop currency,
balance, credit limit or financial parent has changed. The opt-in review now shows
the saved amount/currency alongside actual current values and the proposed effect.
The operator can withdraw that original action or apply a distinct reviewed
replacement. A credit sale above the current limit requires a separate checkbox
for that exact comparison. Checking again or receiving changed values clears the
checkbox; a saved decision is never silently applied to a changed balance.

Original commands, financial record IDs, occurrence times, row images and complete
image bytes stay immutable. Historical payments and undo retain their original
currency under a later shop profile. A new mismatched-currency sale cannot be
converted. Original undo deadlines still apply. Manual counter/khata links and a
JSON backup remain available beside the review.

The wire capsule contains only the selected original financial companions and,
for grouped undo, its actual earlier creation witness. Its source hash covers the
entire original queue row and images. Literal source and command text are hashed
and preserved as text: PostgreSQL JSON operators must not strip or reject Bengali,
escaped NUL or unpaired surrogates. The trusted formatter separately verifies the
complete command, structural IDs, scope, occurrence time, source and saved currency.

Private forced-RLS tickets bind the checked snapshot. Authenticated read/admission
and service-only completion retain original-account/outlet checks, exact credit
consent, stable lock order, server time and reserved financial identity barriers.
Withdrawal writes no money. Replacement uses normal financial validation with a
distinct action ID and produces its actual receipt, without an order revision.
An existing actual original receipt or resolution is checked before new admission
and consent. A genuine result completed elsewhere can differ from a device's last
choice or review nonce, but must match that exact original command and source.

Native schema 24 adds only the internal `moneyReviews` store. Portable backup
schema 10 and its 21-table allowlist stay unchanged. The journal saves token-free
comparisons, deliberate choices and attempts before HTTP. Fresh server tokens
remain ephemeral. Every journal write rechecks the live original phone account,
operator, connection, revision and complete source under native locks. Only a
genuine guarded receipt can acknowledge the original queue action. Canonical
coverage also requires its exact `sync.resolve` audit before retiring the overlay.

If normal guarded sync acknowledges the outcome after the original account is
restored, the historical decision retains its original operator generation. A
separate confirmation-only path rechecks that exact existing receipt with fresh
original-account verification. It validates the full source, receipt prefix,
historical quote and current connection under native locks before annotating the
old journal as confirmed. It cannot revive an old pending choice, submit another
replacement, switch accounts or invent an unavailable server outcome. Account,
operator, source and storage changes during that annotation roll the write back.
