# Payment text parsing and candidate planning

M41 now has executable on-device extraction and amount/time matching in `packages/core/payments.ts` and `payment-matches.ts`. The native persisted Payment, Inbox review interface and original financial-action recovery remain required in this same milestone. M41 is unchecked. This increment adds no product route, automatic money action, backend, provider or configuration prompt.

## Read the full source

`parsePaymentText(raw, context)` accepts the actual captured time, source timezone, outlet currency and optional market, exact sender label and date order. It returns the complete original string, parser version and a frozen copy of the supplied source context, plus proposed amount/currency, transaction reference, full E.164 sender when available, direction and UTC received time. Values are proposals, not proof of a transfer or an authenticated sender.

Incoming receiver grammar covers bKash and Nagad labels and generic bank credit alerts. An unlabelled wallet sentence needs a provider choice; arbitrary strings containing a provider name are not trusted sender labels. Bank grammar describes incoming credits, never an invented card payment or a new bank account. Recognized receipt labels can be mapped to the installation's actual method names by the caller.

Money uses the existing integer-minor-unit parser, including lakh/thousands grouping and Bengali digits. Fees, balances, bare phone/OTP numbers and malformed numeric prefixes do not become a transfer amount. Multiple possible transfer amounts or references remain manual. Outgoing transfers, reversals, refunds, failed payments and verification-code messages remain manual. An unknown format prefills only one explicit currency-qualified amount when it is safe to identify one; it never takes the first of several amounts.

Full sender numbers use the existing market/E.164 rules. Masked digits stay unknown; they are never expanded into a phone number. English numeric dates, unambiguous named-month dates and explicit ISO offsets are supported. Numeric date order and timezone come from the source context. Impossible dates, two-digit years, conflicting/unknown timezone abbreviations, future message times and multiple dates require review. A daylight-saving fold or gap never silently picks one clock occurrence. Missing message time explicitly retains capture time and needs a time check before automatic association. Oversized text and unsupported controls remain available in full for manual handling; no clipped prefix is parsed.

## Find current candidates

`findPaymentTextMatches` reads actual current orders, sales, khata entries/accounts/customers and refunds for the selected business/outlet. It proposes open, priced, pending orders and actual recorded counter/order/khata collection receipts. It excludes foreign scope, another currency/amount, wrong known payer, voided/refunded receipts, debt charges, reminders and reversed collections. An order's older payment receipt never replaces its current receipt. Confirmed used receipt identities are excluded by the native caller.

The default time window is 30 minutes. The caller can explicitly configure a positive window up to one day. All exact eligible candidates are counted, with at most the nearest three returned in stable order. A single recognized incoming candidate can be selected automatically after its received time is known or explicitly checked. Ambiguous or manually parsed sources stay choices. Exact literal snapshots support a later comparison, including complete historical names and notes; a snapshot string is never recording authority.

This function changes no order, counter sale or debt. Associating an incoming source with an open order still needs the actual persisted Payment flow and its explicit money-received action. Linking an existing receipt must not post the same money again. New khata collections need the existing ledger rules and exact allocation/recovery, rather than treating a debt charge as received money.

## Evidence and next work

Thirty committed synthetic messages have independent expected fields, including full text, integer amounts, normalized phones and UTC timestamps. Additional tests cover malformed/outgoing sources, clocks and ambiguity, plus actual domain-generated orders, receipts, collections and reversals. The browser verifier imports the exact modules through a test-only bundled route, checks all thirty fixtures and the unknown-format amount hint in Chromium, and proves that an automatic candidate leaves its pending order unchanged. That test entry is never shipped as a production route.

All 5,378 unit tests pass. The final focused parser/matcher check passes all 95 cases, including a correction that prevents a false ambiguity warning for exactly one unknown-format amount. Both hosting paths pass 58 browser cases covering cash sales, local and customer khata, orders and payment-source verification, including existing offline and five-width accessibility checks. Both builds, final lint and strict types pass. The customer-khata fixture now uses the configured preview origin with the same single-origin allowlist; production origin rules are unchanged. See the [verification record](payment-text-verification.json).

There is no product UI source/import change in this increment. A fresh isolated production build confirms that the parser, matcher and test fixtures are absent from its rendered module graph. The older saved output differs from the current build, so it is not used to claim byte parity. Existing M40 visual evidence remains separate; this groundwork adds no screen or new visual acceptance claim.

The bKash receiver structure is supported by its [published Personal Retail Account documentation](https://www.bkash.com/en/page/personal-retail-account). Dutch-Bangla Bank distinguishes [incoming credit alerts, outgoing debit alerts and balance notices](https://www.dutchbanglabank.com/electronic-banking/sms-alert.html). Nagad and generic bank fixtures define supported synthetic grammar examples; they are not a certification or a promise that every live provider format is supported. Unknown formats keep manual entry.

Next, connect these modules to a proper native Payment record with the complete saved Inbox source and checked fields. Keep its original capture, association and any explicit financial posting separate. Implement ordinary backup/restore, source/selection/revision checks, duplicate/retry protection and receipt/undo recovery before enabling the review interface. The backend-only M37 observed-payment model retains its existing recorded-receipt semantics; it is not an offline substitute for M41. The schema-only public Payment table likewise does not provide a native capture or sync command by itself. Do not encode new machine records into human message text to bypass this work.

All hosting, source/provider accounts, backend settings, credentials, phone numbers and later device enrollment belong to each installation. No maintainer account or verification number is needed for parsing. Workflows, publication, service/migration deployment and tags remain held. M41 stays open until its actual saved-source/manual-review flow and delivery requirements are verified.
